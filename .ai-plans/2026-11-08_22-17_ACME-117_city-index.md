**Design:** No screen: the customer list filters by city exactly as it does now.

## Requirement

ACME-117, in the ticket's words: 95 of every 100 pages answer within about a third of a second, at Northside as at a
small location. After the count step, `bun run sql:top` at 200 a second puts the city filter's count first: 34% of the
database's time, 87 ms a call, because a city that few customers have (Hillcrest: 2 at Northside) is found by reading
the whole location's index (ACME-119 D3: 372 ms for the page, 231 ms for the count, idle).

- **In:** an index that starts with the location and the city, in name order; the "equals" filter on text written so
  an index can serve it, with the same customers as before.
- **Out:** "contains", "starts with" and "ends with" on the city (they stay `ILIKE`; nothing measured needs them);
  the search's count and page (ACME-120 reworks that path); the ticket's other criteria (the count step's plan lists
  where each is delivered).

High-level code:

```ts
// list-columns.ts: "equals" on text, which an index on lower(column) can serve
case "equals":
  return sql`lower(${source}) = lower(${String(value)})`; // both sides folded by Postgres, as ILIKE folds them
```

**Impact:** Breaking changes: None (the parts list's text filters use the same "equals": the same rows, file 6) · Depends on: ACME-119 (text filters on the owner path) · Performance: one more
index on 2.25 million rows (built in seconds on the laptop; `CONCURRENTLY` by hand first in production), every save
of a customer updates it

## Decisions

- D1 The city in the index after the location, then the name order and the id, over an index on the city alone: one
  index finds a city's customers and gives the page in the list's order, and the count reads it alone.
- D2 "Equals" on every text field as `lower(column) = lower(value)`, over keeping `ILIKE`: the same customers (exact,
  case ignored) in a form an expression index can serve; only the city has one.
