## Requirement

At Northside, with the whole desk on Customers at once, the list still opens within about a second and nobody sees an
error; the total is exact up to 10,000 and says "10,000+" past that.

- **In:** the customer list's count stops at 10,001 rows; a text filter (which matches with `ILIKE`) finds its ids
  and count the way a search does; "10,000+" on the customer list, the Home customers tile and the export dialog;
  whatever else the busy-morning check shows stands between the list and none failing (Questions 4).
- **Out:** misspelt names (ACME-120); the export's content (it still writes every customer); parts and stock totals
  (they stay exact, Questions 3).

const { ids, total } =
  query.search || matchesText(CUSTOMER_LIST_COLUMNS, query)
    ? await this.findScopedAsync(userContext.dealerId, locationId, where, order, page, pageSize)
    : await this.findListedAsync(where, order, page, pageSize);

async function findPageAsync(db, where, order, page, pageSize) {
  const rows = await db
    .select({ id: customers.id })
    .from(customers)
    .where(where)
    .orderBy(...order)
    .limit(pageSize)
    .offset(pageOffset(page, pageSize));
  // Counted up to one past the list's depth: past it the screen says "10,000+", and the exact number would cost a
  // read of the whole location on every page (ACME-119).
  const upToDepth = db
    .select({ one: sql`1` })
    .from(customers)
    .where(where)
    .limit(MAX_LIST_DEPTH + 1)
    .as("up_to_depth");
  const [counted] = await db.select({ total: count() }).from(upToDepth);
  return { ids: rows.map((row) => row.id), total: counted?.total ?? 0 };
}

// list-columns.ts (new function)
export function matchesText(columns: ListColumns, query: ListQueryDto): boolean {
  const column = query.filterField ? columns[query.filterField] : undefined;
  return (
    column?.type === "text" && ["contains", "equals", "startsWith", "endsWith"].includes(query.filterOperator ?? "")
  );
}

## Decisions

- D1 `total` stops at 10,001, meaning "more than 10,000", over a new field: the web already reads a total past 10,000
  as "past the limit" (`AppDataGrid.tsx`), so no client learns a new shape. Documented on the customer list handler,
  not on the shared `PageResponseDto`.
- D2 A text filter takes the owner path as a search does, over leaving it under the policy: its `ILIKE` (every text
  operator, even "equals") is not leakproof, so under the policy a city filter read all 1.6 million index entries
  (635 ms). Status and date filters use `=`, `<`, `>` and stay under the policy.
- D4 A search with an exact count (10,000 or fewer matches) is paged through the trigram index only, over leaving it to
  the planner: Postgres guesses `ILIKE` matches poorly, and for "ahed" (no match) walked all 1.6 million customers in name
  order (6.5 s); a term with more than 10,000 matches is dense, so the walk finds a page at once ("gmail": 1 ms walking,
  609 ms through the trigram index).
- D3 A rare city's filter is still the slowest list query (Hillcrest: 372 ms page, 231 ms count as the owner): finding 2
  rows among 1.6 million needs an index that starts with the city. Built only if the busy-morning check names it
  (step 6).
