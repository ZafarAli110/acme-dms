# ACME-121: On a too-busy morning, the system answers at once, does the saves first, and recovers by itself

**Created:** 2026-11-08 20:24

**Status:** Done

## Requirement

When there is more work than the system can do, it answers within about 2 seconds anyway (the answer, or "busy"),
does the saves first, stops work nobody waits for and never anyone else's, keeps its health check answering, and is
back to its calm speed within 10 seconds of the rush ending.

- **In:** a bounded wait for a connection, ending in 503 "busy" with `Retry-After`; connections kept for saves, chosen
  by the request (a POST, PUT, PATCH or DELETE uses them for all its work, its reads too); cancelling a request's
  statement when its caller goes; the health check on a connection of its own; a time limit at the gateway; the load
  test telling "busy" apart and measuring calm before and after the rush.
- **Out:** the web's notice and retries (ACME-122); handling more work (ACME-119 and later); a share per location.

Failure: invalid input, absent data, not allowed, another service down

- [x] An abort after the unit of work ended → cancels nothing (another request on that connection keeps running)
- [x] A save refused as busy → refused before its transaction begins, nothing written; never a busy answer after a
      commit
- [x] The database down → 503 `service-unavailable` as today, never "busy"
- [x] The export worker and the message consumer (no request) → wait as today and are never told "busy"

High-level code:

```ts
// unit-of-work.factory.ts
public async beginAsync(options = { readOnly: false }): Promise<UnitOfWork> {
  const request = currentRequest();                       // null outside a request: worker, consumer, seed
  const pool = request && !request.saves ? this._pools.lists : this._pools.saves;
  const waitMs = !request ? this._backgroundWaitMs : request.saves ? this._saveWaitMs : this._listWaitMs;
  const client = await connectWithinAsync(pool, waitMs, { busy: request !== null }); // DatabaseBusyError when busy
  // BEGIN, the scope as today, and `SELECT pg_backend_pid()` in the same simple query: no extra round trip
  const work = new UnitOfWork(client);
  if (request) {
    const cancel = () => void this.cancelAsync(pid);       // pg_cancel_backend on the cancel pool
    request.signal.addEventListener("abort", cancel, { once: true });
    work.onDispose(() => request.signal.removeEventListener("abort", cancel)); // before the connection goes back
  }
  return work;
}
```

## Decisions

- D1 Saves first by keeping 3 of each copy's 10 connections for them, over a priority queue: a queue still lets a save
  wait behind running lists; kept connections are free when it arrives.
- D2 A request is a save by its method (anything but GET and HEAD), over a flag per unit of work: a save handler's own
  reads (update-part reads before and after its commit) then use the save pool too, so a save is never refused, or
  answered busy after committing, because of a read.
- D3 Busy means "no connection within 1.5 s", over a fixed queue length: the wait is what the person feels.
- D4 Health keeps ACME-117's rule (503 when the database answers slowly or not at all) on a connection of its own, and
  cancels have their own, so neither a full pool nor a burst of cancels looks like a slow database.

- D5 Liveness apart from readiness (the NestJS production checklist, 17): liveness never checks the database, or a
  database outage restarts every copy; readiness (Aspire's check, a load balancer's) keeps ACME-117's rule.
- D6 Drain with `return503OnClosing` (checklist, 3): a copy shutting down refuses new requests at once, so a
  balancer moves them, while those in flight finish; a pre-stop delay belongs to the deployment, when there is one.

- D7 Drain moved out of this plan, measured: it was not one of the ticket's criteria (it came from the NestJS checklist),
  and stopping a copy under load timed out 10 of 4,500 requests because the gateway keeps sending to a copy that has
  gone. A follow-up: passive health checks on the gateway's clusters and a retry for reads whose connection failed.
