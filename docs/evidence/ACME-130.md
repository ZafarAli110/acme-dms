One difference from live remains, chosen by the product owner (D4): no HSTS on a developer's machine. A browser keeps
HSTS per host name, so it would hold every app on `localhost` to HTTPS.

## What these checks don't prove

- **Windows.** Nobody has followed the setup on Windows. The Windows runner tests the certificate check only once
  these commits are pushed (`windows-setup.yml`, on a push to final). `NODE_EXTRA_CA_CERTS=… cmd` in the package
  scripts relies on Bun's script shell setting it there too. The check reads the trusted thumbprint from
  `dotnet dev-certs`'s English output; on another language it exports at every start (safe, slower). This needs a
  person on Windows.
- **The first start's keychain dialog** is shown only by the unit test: forcing a real export would mean deleting
  `.certs/` or touching the keychain. A new machine shows it once.
- **A sign-in that ran out** is shown by ending the session at the server, the same answer the page gets when one
  runs out, not by waiting the hours.
- **The every-page spec** fails on the app's errors and on any 5xx, not on an unexpected 4xx.
- **The cost of HTTPS** cannot be read from one laptop: its runs sit within the swing of the gateway's own. The web
  server's CPU is not in the load watcher's table, and Bun's client speaks HTTP/1.1 to it, where a browser uses HTTP/2.
- **Noted on ACME-130:** the protocols are for a person to add to the ticket; the tracker is not connected to the
  session that built this.
