## What these checks don't prove

- **Which five.** Many customers share the contact date and a surname, and the handler orders by date then surname only.
  Which tied customer fills the fifth row changes between loads (Kieran or Connor Ashhurst at Riverside), and the
  verifier saw two "Ackroyd" rows swap. The ticket says "newest first", which holds; a stable tie-break on `id` is a
  one-line change nobody has asked for. A person decides.
- **Speed at real size.** Northside has 1.6 million customers. The query filters by dealer and location and sorts by
  last contact with `LIMIT 5`; nobody ran `bun run sql:explain` on it, so whether an index serves it is unknown. The
  performance reviewer should check it.
- **The 3 error traces after the browser switch** are the home page's three in-flight requests for the old location
  (`parts`, `customers`, `customers/recent`) cancelled by the browser (`net::ERR_ABORTED`) when the location changed;
  the console shows no errors and the new requests return 200. The cancelled `parts` and `customers` requests don't
  use this change, so it is existing behaviour, not caused by it. The verifier's own report put them down to its 404
  checks; the timestamps and the repeated switch show that is wrong. Whether cancelled requests should be logged as
  errors is not this ticket's.
- **Who was tried in the browser.** Only maria (Northside and Riverside). Sam, rita and tom were checked by API only;
  the web code is unchanged and its query key already includes the location, but no end-to-end browser test was added.
- **A deleted customer and the 400 without a location** are proven by the handler test only; neither was exercised in
  the running system.
- Commands assume the seeded data; `bun run reset` was not run before re-running them.
