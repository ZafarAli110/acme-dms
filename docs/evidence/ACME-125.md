# ACME-125: When a save gets no answer, saving again is always safe: nothing is added twice

Verified 2026-11-10 on final at 9e48616, on `bun run start:prod --load-test` (4 copies, rebuilt with this change; the
migration added `idempotency_records`). The verifier checked every requirement in the running system and returned
PASS.

`api` is `bun run api as <user> [--if-match v] --idempotency-key <key> <METHOD> /api/dealership/v1/…`; it prints
`idempotent-replayed: true` on a replayed answer. A lost answer cannot be made from the command line, so the web's
journeys lose it in the browser with Playwright's `page.route`: "after" lets the request reach the API, then fails
the page's connection; "before" fails it unsent (`web/e2e/save-again.spec.ts`). The verifier ran the customer
journeys again as sam, and once with the answer held past the web's 15 s timeout instead of dropped.

## What these checks don't prove

- **24 hours** is proven only with a fixed clock in a test. The running system would need a day, or a changed
  `expires_at`. A person could check it once on a test environment; nothing else is needed.
- **Busy, a takeover after a 60 s lease, and a failure after the commit** are proven only by the backend HTTP tests,
  which hold the pool, write the record, or fail a read on purpose. None of them can be made safely in the running
  system. They are real Postgres and real handlers, but one process: two API copies taking the same key at once rely
  on the same row lock, and were not tried across copies.
- **"Your first save is still going through"** was never seen on a screen. The API's 409 was checked live, and the web's
  mapping was read in code. A test that holds the first request open in the browser would show it.
- **Bins, stock and a photo on its own** were checked through the API only: there is no screen for them (D1).
- **The cost per save** (two short transactions and one update) was not measured under load. The ACME-117 load test
  with `--writes` would show it.
